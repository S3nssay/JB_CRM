<objective>
Wire deal lifecycle events into existing agent infrastructure -- extend tenancyEventHooks to trigger deal pipelines, add deal-related tools to agents, and implement pipeline step actions that call existing services (checklist, messaging, escalation).

Purpose: This is the glue that makes agents collaborate. When a tenancy is agreed or a sale completes, the event bus triggers the pipeline, and each step's action calls the existing service (checklistService, messageSender, escalationService) that already does the real work.
Output: Deal event emission from CRM routes, pipeline step action implementations, new agent tools, cross-agent conversation access.
</objective>

  <name>Task 1: Pipeline Step Actions and Event Hook Wiring</name>
  <files>server/agents/services/dealPipelineService.ts, server/agents/services/tenancyEventHooks.ts, server/crmRoutes.ts</files>
  <action>
1. Add pipeline step action implementations to dealPipelineService.ts:

   Each pipeline step's `action` field gets a concrete implementation that calls existing services. These are async functions called when a step transitions to 'in_progress':

   LETTINGS_AGREED steps:
   - right_to_rent: Creates deal_event "Right to Rent check initiated", creates notification for admin staff. (Actual check is manual -- step completed by staff via API. Stub per research recommendation for v2 contract features.)
   - ast_contract: Creates deal_event "AST contract generation pending (v2 feature)". Creates notification for admin staff to generate manually. (CONTRACT-01 is v2 scope per research.)
   - deposit_registration: Creates deal_event "Deposit registration task created". Creates notification.
   - inventory_report: Creates deal_event "Inventory report requested". Creates notification.
   - welcome_message: Reads property knowledge base (query property_systems_inventory, property_certifications for emergency contacts, plus tenancy details for move-in date/rent/deposit). Sends welcome message via messageSender to tenant with property-specific info (emergency contacts, bin day from KB, parking info, entry codes). Creates deal_event.
   - checkin_inspection: Creates deal_event "Check-in inspection scheduled for 2 weeks after move-in". Creates a pg-boss delayed job for the PM agent to follow up.

   TENANCY_ENDING steps:
   - offboarding_checklist: Calls checklistService.generateOffboardingChecklist(tenancyId). Creates deal_event.
   - deposit_return: Creates notification for admin staff to process deposit return.
   - checkout_inspection: Creates deal_event and notification for PM staff.
   - condition_report: Creates deal_event after checkout inspection.
   - relist_property: Checks landlord preference (query landlords table for auto-relist preference in notes/dealData). If allowed, creates deal_event "Property relisted". Creates notification for lettings staff.

   RENT_REVIEW steps (per user decision: "Lettings agent does market comparison, proposes increase to landlord, then communicates to tenant. Admin generates Section 13 notice if needed"):
   - market_comparison: Creates deal_event "Market comparison initiated for rent review". Queries comparable properties (properties table filtered by postcode area, bedrooms, property_type) to build a market comparison dataset. Creates notification for lettings staff with comparison data summary.
   - landlord_proposal: Creates deal_event "Rent increase proposal prepared for landlord". Reads market_comparison results from deal.dealData. Drafts rent increase proposal with current rent vs market rate. Creates notification for lettings staff to review and send to landlord.
   - tenant_communication: Creates deal_event "Tenant notified of rent review outcome". Sends rent review communication via messageSender to tenant with new rent amount and effective date. Creates notification.
   - section_13_notice: (isOptional) Creates deal_event "Section 13 notice generation requested". Creates notification for admin staff to generate the formal Section 13 notice if the increase requires statutory notice. Only relevant when tenant does not agree to voluntary increase.

   SALE_AGREED steps:
   - sales_memorandum: Creates deal_event "Sales memorandum generation pending (v2 feature)". Notification.
   - solicitor_notification: Creates deal_event "Solicitor notification pending". Reads solicitor info from deal.dealData. Notification.
   - compliance_checklist: Creates deal_event "AML/ID compliance checklist created". Notification.
   - delist_rental: If property was also listed for rent (check is_listed_rental), creates deal_event "Rental listing removed". Updates property is_listed_rental=false.

   SALE_COLLAPSED steps:
   - relist_property: Creates deal_event "Property relisted after sale collapse". Updates property status.
   - notify_interested_buyers: Queries leads table for leads with property_interest_ids matching this property. Creates deal_event. Sends notification to sales staff with list of buyers to contact.
   - cancel_in_progress: Cancels any in-progress admin tasks (memos, compliance). Creates deal_event.

   Register a stepExecutor function that maps stepId to the correct action and calls it when a step starts.

2. Extend tenancyEventHooks.ts:
   - Import dealEventBus, dealService
   - In the existing tenancy creation hook (or add new): after existing checklist generation, fire-and-forget emit 'tenancy.agreed' with { propertyId, tenancyId, landlordId, tenantId, dealData: { rentAmount, depositAmount, startDate, endDate } }
   - Before emitting: call dealService.createDeal to create the deal record, then dealPipelineService.initializePipeline('lettings_agreed', deal)
   - Add new hook for tenancy status change to 'ending': emit 'tenancy.ending', create deal, init tenancy_ending pipeline
   - Add new hook for tenancy approaching renewal (3 months before end_date): This should be triggered by a pg-boss scheduled job that runs daily, checking tenancies where end_date is ~90 days away. Emit 'lease.renewal_due', create deal, init lease_renewal pipeline.
   - Add annual rent review date detection to the same daily pg-boss scheduled job: Query tenancies where the anniversary of start_date is approaching (within 30 days) and no active rent_review deal exists for that tenancy. For each match, create a deal with dealType='rent_review', init RENT_REVIEW_PIPELINE, emit DEAL_EVENTS.RENT_REVIEW_DUE. This ensures the "Rent review due (annual)" user decision is implemented automatically.

3. Add sale event emission to server/crmRoutes.ts:
   - Import dealEventBus, dealService, dealPipelineService from their respective paths
   - In the offer acceptance handler (wherever an offer status is updated to 'accepted'), add fire-and-forget deal event emission for 'sale.agreed' after offer is marked accepted. Create the deal record via dealService.createDeal with dealType='sale_agreed', then init SALE_AGREED_PIPELINE, then emit event.
   - In the offer cancellation/withdrawal handler (where offer status changes to 'cancelled'/'withdrawn' after previously being 'accepted'), add 'sale.collapsed' emission. Create deal, init SALE_COLLAPSED_PIPELINE, emit event.
   - Follow the tenancyEventHooks fire-and-forget IIFE pattern. Do NOT modify the route response flow -- all deal event emission is async fire-and-forget.

<task type="auto">
  <name>Task 2: Agent Deal Tools and Cross-Agent Conversation Access</name>
  <files>server/agents/sdk/tools.ts, server/agents/sdk/adminAgent.ts, server/agents/sdk/lettingsAgent.ts, server/agents/sdk/salesAgent.ts, server/agents/sdk/pmAgent.ts</files>
  <action>
1. Add new deal-related SDK tools to server/agents/sdk/tools.ts:

   - emitDealEventTool: Allows agents to emit domain events during conversations. Input: { eventType: string, dealId: number, metadata: object }. Calls dealEventBus.emit. Used when an agent detects a deal-relevant change during a conversation (e.g., lettings agent agrees rent with tenant).

   - readDealStatusTool: Allows agents to check deal progress. Input: { dealId?: number, propertyId?: number }. Returns deal with step statuses. Agents use this to understand what other agents have done before acting.

   - queryContactConversationsTool: Cross-agent conversation access per user decision. Input: { contactId: number, agentType?: string, limit?: number }. Calls conversationStore.getConversationsForContact, optionally filtered by agent type. Returns conversation summaries with last message. This implements the "any agent can query full conversation history for a contact" requirement.

   - flagInconsistencyTool: Inconsistency detection per user decision. Input: { dealId: number, field: string, existingValue: string, newValue: string, source: string }. Creates a notification of type 'inconsistency' for relevant staff. Creates deal_event. Start simple: exact field comparison for critical fields (rent amount, deposit, pet policy, number of occupants) per research recommendation.

   - emitCrossReferralTool: Cross-referral between departments per user decision. Input: { fromDepartment: string, toDepartment: string, contactId: number, reason: string, propertyId?: number }. Creates a lead in the target department. Creates deal_event. Creates notification for target department staff.

   All tools follow the existing wrapRegistryTool pattern with zod4 schemas.

2. Add deal tools to agent tool arrays:
   - adminAgent.ts: Add readDealStatusTool (Admin reads deal to know what's pending)
   - lettingsAgent.ts: Add emitDealEventTool, readDealStatusTool, emitCrossReferralTool (Lettings can trigger deal events and cross-refer to sales)
   - salesAgent.ts: Add emitDealEventTool, readDealStatusTool, emitCrossReferralTool (Sales can trigger deal events and cross-refer to lettings)
   - pmAgent.ts: Add readDealStatusTool, queryContactConversationsTool, flagInconsistencyTool (PM reads deal state, accesses cross-agent conversations, flags data inconsistencies)

3. Cross-agent conversation access:
   - The queryContactConversationsTool already leverages conversationStore.getConversationsForContact which exists from Phase 1. The tool just wraps it for SDK access.
   - Add a helper in conversationStore (if not already present) to filter conversations by agent_type metadata.
  </action>
